System design

03. Proposed architecture

A modular monolith is the right first architecture: one FastAPI application, clearly separated services, a persistent vector store and a small metadata database. This is easier to build, test and explain than unnecessary microservices.

Neon stores document records and canonical chunk text/metadata. Pinecone stores 384-dimensional BGE vectors and lightweight metadata IDs for filtering. Retrieved IDs are resolved to full chunk text in Neon.

Neon owns the canonical records

Suggested tables: documents (id, filename, SHA-256, MIME type, status, timestamps) and chunks (id, document_id, text, page/section, chunk_index). Use a foreign key with cascade delete for chunk rows.

Pinecone owns vector retrieval

Use one dense index with dimension 384 and cosine metric. Vector IDs map to Neon chunk IDs; metadata includes document_id, chunk_id, filename, page and chunk index for filtering/citations.

Cross-store deletion safety: Neon and Pinecone cannot share one ACID transaction. Mark the document as deleting, delete Pinecone vectors by document_id, then delete Neon records. If Pinecone fails, retain the tombstone/status and retry; never report deletion success while vectors may remain searchable.

End-to-end data flows

Flow A — Upload and ingest a document
  1. Browser sends a multipart upload to the document endpoint.
  2. Validate extension, MIME type, file size, non-empty content and supported format.
  3. Calculate SHA-256. If the same content already exists, return 409 Conflict.
  4. Extract text while preserving PDF page numbers or DOCX section/paragraph context as available.
  5. Reject files with no extractable text. Scanned-PDF OCR is a separately approved enhancement, not silently assumed.
  6. Split text into chunks and attach document ID, filename, page/section and chunk index.
  7. Create embeddings and persist vectors; write document status and metadata.
  8. Return success only when the document is searchable and show it in the frontend list.
Flow B — Ask a question
  1. Validate the question and apply input guardrails.
  2. Embed the question and search the vector collection using the selected similarity metric.
  3. Apply the configured top-k and calibrated threshold; retain exact chunk IDs and scores.
  4. If evidence is insufficient, return a clear “not found in the provided documents” response.
  5. Otherwise send only the retrieved evidence and question to the LLM with strict grounding instructions.
  6. Validate every returned citation against the set of retrieved chunk IDs.
  7. Return the answer, citations, retrieved chunks, count and scores to the UI.
Flow C — Delete a document
  1. Confirm that the document ID exists.
  2. Delete all vectors filtered by that document ID.
  3. Delete or mark the document metadata record according to the approved deletion policy.
  4. Verify that a follow-up query cannot retrieve the deleted document's chunks.
  5. Return 204 No Content only after deletion is complete.

25+

Metrics and comparison

MetricWhat it tells usHow we report it
Hit Rate@kWhether at least one relevant source appears in the top-k results.Percentage of questions with a hit.
Recall@kHow many of the labelled relevant chunks are retrieved in the top-k.Mean recall across answerable questions.
MRRHow highly the first relevant result is ranked.Mean reciprocal rank.
FaithfulnessWhether answer claims are supported by retrieved context.RAGAS/justified judge score plus manual spot checks.
Answer correctnessWhether the answer matches the reference answer.Rubric-based assessment, with judge/manual verification.
Abstention qualityWhether unanswerable questions are correctly refused without fabricated citations.Correct abstentions and false-answer cases.
Latency / costOperational speed and approximate expense per question.Average and p50/p95 where sample size supports it; token/cost estimates when provider usage is available.

Reproducible evaluation procedure

  1. Freeze the corpus and golden set version.
  2. Run Configuration A and save raw retrieved results.
  3. Run Configuration B against the exact same questions.
  4. Calculate Hit Rate@k, Recall@k and MRR with the same relevance labels.
  5. Evaluate answer faithfulness, correctness and unanswerable handling.
  6. Inspect failures and explain why they happened.
  7. Choose the better configuration using measured results and document trade-offs in EVAL.md.
No fabricated results: Metrics must come from executed experiments. If a metric has not been run, label it “not measured” rather than filling in a plausible-looking number.
Reliability and safety

09. Guardrails, errors and test strategy

Input and upload checks

  • Empty, whitespace-only or overly long questions
  • Unsupported file type and MIME mismatch
  • Zero-byte, corrupt or text-empty files
  • Maximum upload size and bounded extraction
  • Prompt injection / jailbreak attempts in questions

Output and document checks

  • Uploaded content is untrusted data, not instructions
  • Answers must be supported by retrieved evidence
  • Citations must belong to retrieved chunk IDs
  • Abstain when evidence is insufficient
  • Never expose system prompts, secrets or API keys

HTTP error contract

StatusUseValidation case
200Successful search, answer or listingNormal question and document listing
201Document created and ingestedValid PDF/DOCX upload
204Document deletedDelete existing document
400Empty file or no extractable textEmpty or scanned-only PDF without OCR
404Document not foundDelete/read unknown ID
409Duplicate contentUpload same file twice
415Unsupported media typeUpload an unsupported extension/type
422Invalid request dataMalformed question payload
429Rate limit exceededRate-limit test if configured
503Required provider/storage unavailableMock timeout or provider outage

Test layers

  • Unit tests: extraction, hashing, duplicate detection, chunk metadata, citation validation, thresholds and guardrails.
  • API tests: upload/list/ask/delete, response schemas, status codes and error handling using FastAPI TestClient.
  • Integration tests: local vector persistence and one controlled real-provider smoke test; mock paid APIs in routine tests.
  • Regression tests: after deletion, deleted chunks must never be returned; every citation must map to retrieved evidence.
  • Notebooks: demonstrate extraction, chunking, embeddings/retrieval and answering step by step, as required by the brief.
  • Documentation quality: module/class/function docstrings, useful inline comments for non-obvious logic, type hints, clear README setup instructions and architecture/decision records.
